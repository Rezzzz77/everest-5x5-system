## ۲. مدل کسب‌وکار در یک نگاه

سیستم پنج‌مرحله‌ای رشد تیم فروش:

1. **شروع (۷۲ ساعت)** — هدف، داستان، لیست ۳۰ نفره، ۲۰ دعوت، اولین ارائه
2. **حرکت (۷ روز)** — ۵ عادت روزانه + زنجیره ۷ روزه + گزارش شبانه
3. **ساخت (۳۰ روز)** — دانش محصول، آدم‌یابی، لیست ۱۰۰+، دعوت، پیگیری
4. **تکثیر (۹۰ روز)** — چرخه ۵ گامی: یاد بگیر → انجام بده → نشان بده → همراهی کن → واگذار کن
5. **راهبری (مستمر)** — داشبورد KPI، جلسات هدفمند، ۵ استاندارد راهبر

مرحله بعدی فقط با تکمیل «معیار عبور» مرحله قبل باز می‌شود (`getHighestUnlockedStage`).

## ۴. تصمیم‌های ثبت‌شده (ADR سبک)

### D1 — Offline-first، نه Cloud-first
اپ باید بدون اینترنت کامل کار کند (کاربران میدانی فروش).
→ `localStorage` منبع حقیقت محلی؛ Supabase فقط آینه (mirror).
→ اگر Supabase تنظیم نشده باشد، اپ باید **بی‌صدا** آفلاین کار کند.

### D2 — Supabase بدون Auth در MVP
برای رسیدن سریع به نسخه قابل استفاده، `anon key` + RLS سهل‌گیرانه.
⚠️ **بدهی فنی شناخته‌شده** — جزئیات در `docs/SECURITY.md`.
هیچ داده حساس (کد ملی، شماره تماس) نباید تا فعال‌سازی Auth به‌صورت عمومی بماند.

### D6 — ورود با OTP ایمیل، نه رمز
رمز نگهداری نمی‌کنیم؛ کد یک‌بارمصرف ایمیل + نشست JWT.
دلیل: کاربران میدانی رمز را فراموش می‌کنند و بازیابی رمز = پشتیبانی بیشتر.
حالت «بدون حساب» برای تست آفلاین نگه داشته شد (بدون ذخیره ابری).

### D7 — کد ملی در جدول جدا (`profiles`)
`user_state.state_data` یک JSON بزرگ است؛ داده حساس نباید داخلش باشد.
`profiles` ستون‌محور است و RLS مخصوص خودش را دارد.

### D3 — تفکیک ماژول‌ها
`app.js` = رفتار · `src/db.js` = داده · `src/defaults.js` = محتوا · `src/config.js` = کلیدها.
محتوا (مراحل، ویژگی‌ها، محصولات) باید بدون دست‌زدن به منطق قابل ویرایش باشد.

### D5 — کلید عمومی پروژه در `src/env.js`، override با `localStorage`
**بازنگری‌شده (نسخه ۰.۹.۴):** تصمیم قبلی «هیچ کلیدی در کد نباشد» عملاً باعث شده بود
بک‌اند برای هیچ کاربری کار نکند (هر نفر باید پروژه Supabase خودش را می‌ساخت و
schema را اجرا می‌کرد). حالا:

- `src/env.js` فقط شامل **URL پروژه + کلید anon/publishable** است. این دو عمومی‌اند
  و در هر PWA قابل مشاهده‌اند؛ به همین دلیل انتشارشان «لو رفتن راز» نیست.
- مرز امنیت واقعی **RLS** است: `anon` هیچ grant/policy ندارد؛ فقط `authenticated`
  با `user_id = auth.uid()` به ردیف خودش دسترسی دارد (`supabase/schema.sql`).
- `getSupabaseConfig()` اول `localStorage` (مودال ☁️) را می‌خواند، بعد `env.js`.
  هر تیم می‌تواند پروژه خودش را جایگزین کند.
- ❌ `sb_secret_*` / `service_role` / توکن مدیریتی `sbp_*` هرگز در کلاینت نیست؛
  `validateConfig()` کلید secret را رد می‌کند و تست خودکار هم بررسی می‌کند.

### D4 — گراف دانش به‌عنوان ابزار توسعه
`tools/build_graph.py` گراف را از منبع تولید می‌کند (نه دستی).
بعد از هر تغییر ساختاری باید دوباره اجرا و کامیت شود.

## ۶.۶ مسیر ورود (چطور کار می‌کند)

1. کاربر ایمیل می‌زند → `sendOtp()` → `POST /auth/v1/otp`
2. کد ۶ رقمی می‌آید → `verifyOtp()` → `POST /auth/v1/verify` → نشست با `access_token`
3. `saveSession()` در `localStorage` (با `expires_at`)
4. هر درخواست داده: `authHeaders()` → `Bearer <access_token>`
5. RLS سمت دیتابیس: `user_id = auth.uid()` → کاربر فقط ردیف خودش
6. انقضا: `getAccessToken()` خودکار `refresh_token` می‌زند
7. خروج: `signOut()` → `POST /auth/v1/logout` + `clearSession()`

## ۷.۵ اتصال Supabase — معماری امن (بدون کلید پیش‌فرض)

> **پیش‌فرض پروژه در `src/env.js` است** (URL + کلید anon عمومی). کاربر می‌تواند
> با دکمه ☁️ پروژه خودش را جایگزین کند. پیش‌نیاز: `supabase/schema.sql` در آن پروژه اجرا شده باشد.

| مورد | وضعیت |
|------|-------|
| Project URL | تنظیم شده توسط کاربر در اپ (دکمه ☁️) |
| کلید کلاینت | تنظیم شده توسط کاربر در اپ (فقط `sb_publishable_*` یا `eyJ...`) |
| نوع کلید | سبک جدید Supabase (publishable) — نه JWT |
| جدول `user_state` | می‌سازد با اجرای `supabase/schema.sql` |
| جدول `profiles` | می‌سازد با اجرای `supabase/schema.sql` |
| RLS | سخت‌گیرانه (`user_id = auth.uid()`) فعال پس از اجرای SQL |

### مدل دسترسی (نسخه ۰.۴)
```
anon  ──(فقط /auth/v1)──► OTP ایمیل ──► JWT
authenticated ──RLS (user_id = auth.uid())──► user_state, profiles
anon  ──✖──► user_state, profiles   (revoke + no policy)
```

### کلیدهای جدید Supabase (مهم برای آینده)
- `sb_publishable_*` → عمومی، برای کلاینت. فقط در اپ وارد می‌شود، در کد نیست.
- `sb_secret_*` → **فقط سرور**. هرگز در کلاینت نگذار (کد با پیام صریح رد می‌کند).
- `anon`/`service_role` (JWT) تا پایان ۲۰۲۶ منسوخ می‌شوند → کد از ابتدا با کلید جدید نوشته شد.

## ۸. قدم بعدی مشخص

**بلوکه‌ی فعلی: هر تیم باید پروژه Supabase خود را راه‌اندازی کند.**

مراحل برای هر تیم/کاربر:
1. در [Supabase Dashboard](https://supabase.com/dashboard) پروژه جدید بسازید
2. **SQL Editor** → محتوای `supabase/schema.sql` را اجرا کنید (idempotent)
3. **Authentication → Providers → Email** → فعال‌سازی *Enable email OTP / Magic Link*
4. در اپ: دکمه **☁️** → Project URL و anon key را وارد کنید
5. **تست اتصال** → باید سبز شود
6. **ذخیره و همگام‌سازی**

هشدار: SMTP پیش‌فرض رایگان Supabase محدودیت ارسال دارد؛ برای تیم واقعی
یک SMTP اختصاصی (Resend/SendGrid) وصل کنید، وگرنه OTP به بعضی ایمیل‌ها نمی‌رسد.

پس از اجرا:
1. در اپ: ثبت‌نام با ایمیل → کد ۶ رقمی → تغییر یک چک‌باکس
2. نشانگر بالای صفحه باید «ابر ✓» شود
3. داده‌ها در Supabase پروژه‌ی شما ذخیره می‌شوند (RLS تضمین می‌کند فقط شما می‌بینید)

اگر همه سبز شد، قدم بعدی: **ایجنت Coach** (پیشنهاد اقدام بعدی بر اساس وضعیت مراحل).
